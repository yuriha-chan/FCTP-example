# P0 world-operation contracts

This inventory maps client intentions to the world operations that exist and the evidence required before calling an outcome complete. An accepted HTTP request is not evidence of later movement or job completion. The application API paths are specified in `frontend-technical-requirements.md`; the paths below belong to world servers.

| Intention | Existing handler / method and path | Input and authorization | Result and completion evidence |
| --- | --- | --- | --- |
| Issue or rotate a native token | `apps/test-authority/src/home.ts`, POST `/local/home/issue`, `/local/home/rotate` | Optional `actor`; Home administrator credential | Returns Actor and native token; rotation redistributes digests to known resource Actors. Handle/password login and account availability are absent; task 02 adds them. |
| Request entry | `apps/test-authority/src/registry.ts:sendEntry`, POST `/local/registry/entry` | `territory`, `port`, `route`, optional `cargo` and `vessel`; administrator or authenticated vessel possessor | Returns `EntryRequest` with HTTP 202. Territory acceptance and `BerthingEvent` establish a local visit; `EntryRejected` establishes rejection. A pending request is neither admission nor berthing. |
| Request departure | `apps/test-authority/src/registry.ts:sendDeparture`, POST `/local/registry/departure` | `territory`, `port`, optional `route` and `vessel`; administrator or authenticated possessor | Returns `DepartureRequest` with HTTP 202. Territory `DepartureEvent` establishes departure; signed `ExitEvent` establishes exit and supplies evidence for the next entry. |
| Change Registry cargo adoption | `apps/test-authority/src/registry.ts:switchAdoption`, POST `/local/registry/adoption` | Boolean `adoption`, optional `vessel`; administrator or authenticated possessor | Returns changed Registry setting; Registry observations after subsequent cargo events are evidence of adoption, not a change in Territory stocks. |
| Mine, manufacture, transfer in policy Territory | `apps/territory-policy/src/app.ts`, POST `/local/mine`, `/local/manufacture`, `/local/transfer` | `count`; optional mine `variety`, manufacture `recipe`, transfer `variety` and `direction`; authenticated player | Immediate result or domain failure; refreshed Territory state confirms shared stock changes. |
| Load or unload in policy Territory | `apps/territory-policy/src/app.ts`, POST `/local/load`, `/local/unload` | `vessel`, `variety`, `count`; authenticated player with matching possessor and active visit | Immediate result and changed local cargo/stock; emitted `CargoOperationEvent` can update Registry cargo independently. |
| Mine or manufacture in simulation Territory | `apps/territory-sim/src/app.ts`, POST `/local/mine`, `/local/manufacture` | Mine `count`, optional `duration`; manufacture `count` and `recipe` (`native` or `imported`); authenticated player | Returns a job. State/job progress and eventual stock change after administrator-controlled ticks establish completion. |
| Load or unload in simulation Territory | `apps/territory-sim/src/app.ts`, POST `/local/load`, `/local/unload` | `entryRequest`, cargo manifest and `duration`; authenticated possessor of the visit | Returns handling job. Completion after a tick changes local cargo and emits `CargoOperationEvent`; Registry cargo may reflect it separately. |
| Read and publish player creations | `apps/test-authority/src/authoring.ts:installAuthoring`, GET `/local/authoring`, POST `/local/authoring/assets`, `/local/authoring/varieties` | Asset `name`, `text`; Variety `name`, `mass`, `version`, optional `asset` and `production`; native authenticated player | POST returns created identity with HTTP 201. Read-back of the creation/publication is separate evidence; linking an owned Asset to a Variety can produce a grant. |
| Change policy or admission configuration | `apps/territory-policy/src/app.ts`, POST `/local/admin/policy`, `/local/admin/admission` | Policy object or partial admission fields (`registryAcceptance`, `territoryAcceptance`, `publicPorts`, `mismatchPolicy`, `reviewMode`); Territory administrator credential | Returns configuration; refreshed `/local/state` confirms values. Manual `EntryRequest` review is available through GET `/local/admin/entry-requests` and POST `/local/admin/entry-requests/:requestId/approve` or `/reject`; approval resumes acceptance and rejection emits `EntryRejected`. |
| Change simulation facilities or advance time | `apps/territory-sim/src/app.ts`, POST `/local/admin/facilities`, `/local/admin/tick` | Partial `mining`, `manufacturing`, `port` facilities or no required tick body; Territory administrator credential | Returns result/state; refreshed state, jobs, visits, and emitted events establish effects of the change or tick. Page reads must not advance time. |
| Inspect Registry fleet | `apps/test-authority/src/registry.ts`, GET `/local/registry/fleet` | Registry administrator credential | Returns fleet observation; this is not a movement operation. |

Existing action discovery: `GET /local/registry/actions?vessel=...`, `GET /local/actions?vessel=...` on both Territories. Policy discovery advertises a `traverse` example for each explicitly published route from the active visit's port to another owned port. Read-only state endpoints expose distinct Registry, policy and simulation observations. The application must not treat action descriptions as completed operations.

## Territory entry, exit, and route legs

| Leg or decision | Existing route and handler | Required outcome or missing implementation |
| --- | --- | --- |
| Policy west boundary → East Haven | `apps/territory-policy/src/app.ts` publishes `Route { id, type, name, from, to }`. `apps/territory-policy/src/territory.ts` handles the verified Registry `EntryRequest`. | Registry entry request names the port and route; accepted request creates visit and `BerthingEvent` establishes arrival at that port. The route does not itself perform a separate motion operation. |
| Policy East Haven → West Haven | `apps/territory-policy/src/territory.ts` POST `/local/traverse` with `{ vessel, route }`; the route must be explicitly published and start at the current port with another owned port as destination. | The authenticated active visit possessor receives the authoritative `VoyageEvent { kind: 'local-movement', details: { from, to, route, entryRequest } }`; the persisted visit moves to the destination port and route while retaining cargo and entry identity. Invalid, reverse, unowned, or wrong-start routes never move the visit; `GET /local/actions` advertises available `traverse` examples. |
| Policy port → exit | `apps/territory-policy/src/territory.ts` handles `DepartureRequest`; an explicitly published route from the current port may be supplied instead of the entry route. | `DepartureEvent` and signed `ExitEvent` establish departure and exit. The signed `ExitEvent.route` identifies the actual departure route. Routes are never inferred in reverse; no reverse port-to-boundary edge is invented. |
| Simulation east boundary → main port | `apps/territory-sim/src/app.ts` publishes `Route { from, to, distance }`; `apps/territory-sim/src/territory.ts` handles `EntryRequest`. | Accepted request creates a pending visit; later tick and `BerthingEvent` establish arrival. A successful entry POST is not completion. |
| Simulation port → exit | `apps/territory-sim/src/territory.ts` handles `DepartureRequest`. | Later tick emits `DepartureEvent` and signed `ExitEvent`; no reverse route or boundary-position event is advertised. |
| Simulation port → port | Only one port and a boundary-to-port route were found in the configured simulation Territory. | No advertised leg in the existing fixture; do not add a fictional connection. |

For a cross-Territory journey, Registry-proven exit from the first Territory is passed as evidence on the next entry; destination `BerthingEvent` establishes the next local visit. Manual review of incoming `EntryRequest` is missing in both Territory handlers. Task 10 adds opt-in pending review and administrator decisions, preserving automatic admission by default. Approval resumes acceptance; rejection emits `EntryRejected`. A decision result is not itself berthing.
